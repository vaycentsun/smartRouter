# Smart Router P0 功能实现

## 概述

实现 ROADMAP 中 3 个 P0 功能：**高级分析仪表盘**、**Playground 交互界面**、**告警系统**。按批次递进实现，数据层先做，交互和监控随后跟进。

## 背景与动机

当前 Smart Router 已具备基础 Token 统计（按模型汇总），但缺少：
- 时间维度的趋势分析（无法回答"本周花了多少"）
- 模型交互测试工具（用户无法快速对比不同模型效果）
- 成本/错误率超限告警（需要人工巡检日志）

## 目标

- **批次1**：建立时间序列数据层，前端展示成本趋势、模型使用量对比、Token TOP10
- **批次2**：提供单模型测试和多模型并发对比的交互界面，显示响应、延迟、预估成本
- **批次3**：支持按成本/请求数/错误率阈值告警，通过 Webhook 和日志通知

## 非目标

- 不对接服务商真实账单 API（延迟高、覆盖率低）
- 不引入外部数据库（保持 SQLite/JSON 的轻量方案）
- 不做分布式告警（如短信、邮件 SMTP）
- 不做 LLM 自动评估（Playground 只展示原始响应，不评分）
- 不做用户反馈学习（P4 功能）

## 设计方案

### 架构概述

三个批次共享同一套时间序列数据基础设施：

```
请求 → SmartRouterMiddleware → TokenStats.record() → token_stats.json
                                          ↓
                                   daily_records (按日聚合)
                                          ↓
              ┌───────────────────────────┼───────────────────────────┐
              ▼                           ▼                           ▼
        /api/analytics/*           /api/playground             Alert Checker
        数据分析仪表盘              交互测试界面                 定时告警检查
```

### 组件设计

#### 组件 1: TokenStats（改造）
**职责**: 按日聚合记录每次请求的 token 用量，保持向后兼容
**位置**: `core/smart_router/utils/token_stats.py`
**接口**:
```python
class TokenStats:
    async def record(self, model: str, prompt_tokens: int, completion_tokens: int, total_tokens: int)
    def get_all(self) -> dict  # 累计汇总（向后兼容）
    def get_daily(self, date_str: str) -> dict  # 某日数据
    def get_daily_range(self, start_date: str, end_date: str) -> dict  # 日期范围
    def get_summary(self, days: int = 7) -> dict  # 近 N 天汇总
```
**存储格式** (`token_stats.json`):
```json
{
  "version": 2,
  "records": { "model_name": { "prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0, "request_count": 0 } },
  "daily_records": {
    "2026-05-05": { "model_name": { "prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0, "request_count": 0 } }
  },
  "_meta": { "last_updated": "2026-05-05T13:00:00Z" }
}
```
**依赖**:
- 现有 `token_stats.json`（v1 格式需自动升级）
- `asyncio.Lock`（并发安全）

#### 组件 2: Analytics API
**职责**: 提供时间范围聚合查询接口
**位置**: `core/smart_router/gateway/dashboard_api.py`
**接口**:
```python
async def analytics_summary(days: int = 7) -> dict
async def analytics_daily(days: int = 7) -> list[dict]
async def analytics_by_model(days: int = 7) -> list[dict]
async def analytics_top_models(limit: int = 10, days: int = 7) -> list[dict]
```
**端点**:
| 端点 | 参数 | 返回 |
|------|------|------|
| `GET /api/analytics/summary` | `days` (默认7, 最大90) | 总成本、总请求、总token、日均 |
| `GET /api/analytics/daily` | `days` | 每日数组: `{date, cost, requests, tokens}` |
| `GET /api/analytics/by-model` | `days` | 按模型: `{model, prompt_tokens, completion_tokens, cost, request_count}` |
| `GET /api/analytics/top-models` | `limit`, `days` | TOP N: `{model, total_tokens, cost, request_count}` |

**成本计算**:
```python
cost = (prompt_tokens / 1000 * price.prompt_per_1k) + (completion_tokens / 1000 * price.completion_per_1k)
```
单价从 `models.yaml` 的 `price` 字段读取。缺失时成本为 `None`。

**汇总时缺失单价的处理**:
- 按模型聚合（`/api/analytics/by-model`）：无单价的模型成本字段为 `None`
- 总体汇总（`/api/analytics/summary`）：跳过无单价的模型，仅对「有单价的模型」求和；返回 `{"total_cost": 12.5, "incomplete": true}`，`incomplete=true` 表示部分模型未计入
- 前端：总成本旁显示 `*` 提示"部分模型未配置单价"

**依赖**:
- `TokenStats`
- `ConfigLoader`（读取模型单价配置）

#### 组件 5: Playground API
**职责**: 支持单模型测试和多模型并发对比
**位置**: `core/smart_router/gateway/playground_api.py`（新增文件）
**注册方式**: 在 `dashboard_api.py` 的 `build_dashboard_app()` 中通过 `app.include_router(playground_router, prefix="/api/playground")` 注册
**接口**:
```python
class PlaygroundRequest(BaseModel):
    mode: Literal["single", "compare"]
    prompt: str
    models: list[str]
    stream: bool = False

class PlaygroundResult(BaseModel):
    model: str
    provider: str
    response: str
    latency_ms: int
    prompt_tokens: int
    completion_tokens: int
    estimated_cost: float | None
    error: str | None
    routing_info: dict | None  # 复用 DryRun 输出结构: {task_type, strategy, score, reason}

async def playground_completions(request: PlaygroundRequest) -> list[PlaygroundResult]
async def playground_history() -> list[dict]
async def playground_delete_history(record_id: str) -> dict
```
**端点**:
| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/playground/completions` | POST | 发送请求，返回结果列表 |
| `/api/playground/history` | GET | 查询历史记录 |
| `/api/playground/history/{id}` | DELETE | 删除单条记录 |

**并发策略**:
- `compare` 模式：使用 `asyncio.gather()` 并发请求
- 每个模型通过 LiteLLM `acompletion()` 调用
- 超时 30 秒，超时的模型返回 `error: "请求超时"`
- 最多同时对比 3 个模型
- **防速率限制**: 并发请求前增加 500ms stagger 间隔（第1个立即发，第2个等500ms，第3个等1000ms）

**历史记录存储**:
- 文件: `~/.smart-router/playground_history.json`
- 最多保留 50 条，FIFO 淘汰

**依赖**:
- `litellm.acompletion()`
- `TokenStats`（可选，记录 Playground 请求）

#### 组件 7: Alert 配置与检查器
**职责**: 告警规则管理和定时检查
**位置**: `core/smart_router/alerts/`（新增模块）
**配置格式** (`~/.smart-router/alerts.yaml`):
```yaml
alerts:
  - id: "alert-001"
    name: "每日成本超限"
    enabled: true
    condition:
      metric: "daily_cost"
      operator: ">"
      threshold: 10
    time_window: "1d"
    severity: "warning"
    channels:
      - type: "webhook"
        url: "https://hooks.slack.com/..."
      - type: "log"
    cooldown_minutes: 60
```
**支持的 metrics**:
- `daily_cost` — 当日累计成本（CNY/USD）
- `daily_requests` — 当日请求数
- `daily_tokens` — 当日 token 总数
- `error_rate` — 近 5 分钟错误率（基于内存滑动窗口计数器）

**AlertChecker 接口**:
```python
class AlertChecker:
    def __init__(self, config_path: Path, token_stats: TokenStats, error_counter: ErrorCounter)
    async def check_all(self) -> list[AlertTrigger]
    async def send_notification(self, alert: AlertRule, trigger: AlertTrigger, channel: AlertChannel)
```

**ErrorCounter（新增，内存滑动窗口）**:
```python
class ErrorCounter:
    """基于内存的 5 分钟滑动窗口错误计数器"""
    def record(self, status_code: int)
    def get_error_rate(self) -> float  # 近 5 分钟错误率 (0.0 ~ 1.0)
```
- 由 `SmartRouterMiddleware` 在请求返回非 2xx 时调用 `error_counter.record(status_code)`
- 使用 `collections.deque` 存储最近 5 分钟的时间戳，内存占用恒定

**检查策略**:
- 独立后台协程，每 60 秒执行一次 `check_all()`
- 读取 `alerts.yaml` 中的规则
- 对每个启用的规则，计算当前 metric 值：
  - `daily_cost` / `daily_requests` / `daily_tokens`: 读取今日 `daily_records`，按 `time_window` 汇总（`"1d"` 表示今日，`"7d"` 表示近7天）
  - `error_rate`: 读取 `ErrorCounter.get_error_rate()`，忽略 `time_window`
- 条件满足且不在冷却期内 → 触发告警
- 触发后写入 `~/.smart-router/alerts_history.json`

**Alert 数据模型**:
```python
class AlertCondition(BaseModel):
    metric: Literal["daily_cost", "daily_requests", "daily_tokens", "error_rate"]
    operator: Literal[">", "<", ">=", "<="]
    threshold: float

class AlertChannel(BaseModel):
    type: Literal["webhook", "log"]
    url: str | None = None  # webhook 必填，log 忽略

class AlertRule(BaseModel):
    id: str
    name: str
    enabled: bool
    condition: AlertCondition
    severity: Literal["info", "warning", "critical"] = "warning"
    time_window: str = "1d"  # "1d" | "7d" | "30d"；error_rate 忽略此字段
    channels: list[AlertChannel]
    cooldown_minutes: int = 60

class AlertTrigger(BaseModel):
    rule_id: str
    timestamp: str
    metric: str
    current_value: float
    threshold: float

class AlertHistory(BaseModel):
    id: str
    rule_id: str
    rule_name: str
    severity: str
    metric: str
    current_value: float
    threshold: float
    timestamp: str
    status: Literal["success", "failed"]  # 通知发送状态
    channel_type: str
```

**新增 Alert API 端点**:
| 端点 | 方法 | 请求体 | 返回 |
|------|------|--------|------|
| `/api/alerts/rules` | GET | — | `{rules: AlertRule[]}` |
| `/api/alerts/rules` | POST | `AlertRule` | `{success: bool, id?: string}` |
| `/api/alerts/rules/{id}` | PUT | `AlertRule` | `{success: bool}` |
| `/api/alerts/rules/{id}` | DELETE | — | `{success: bool}` |
| `/api/alerts/history` | GET | `?limit=50` | `{history: AlertHistory[]}` |
| `/api/alerts/test` | POST | `{channel: AlertChannel}` | `{success: bool, message?: string}` |

**Webhook payload**:
```json
{
  "alert_name": "每日成本超限",
  "severity": "warning",
  "metric": "daily_cost",
  "current_value": 15.3,
  "threshold": 10,
  "timestamp": "2026-05-05T13:00:00Z",
  "message": "Smart Router 告警：每日成本 15.3 CNY，超过阈值 10 CNY"
}
```

**日志输出**:
写入 `~/.smart-router/alerts.log`，格式：
```
[2026-05-05 13:00:00] [WARNING] 每日成本超限: daily_cost=15.3 > threshold=10
```

**依赖**:
- `TokenStats.get_daily_range()`
- `httpx`（发送 Webhook，新增依赖）
- `aiofiles`（可选，异步文件写入）

### 数据流

#### 批次1 数据流

```
1. 用户发送请求 → /v1/chat/completions
2. SmartRouterMiddleware 拦截响应
3. 解析 usage → TokenStats.record(model, prompt, completion, total)
4. TokenStats 同时更新:
   - records[model]（累计值，向后兼容）
   - daily_records[YYYY-MM-DD][model]（每日值）
5. 前端 fetchAll() → /api/analytics/summary + daily + by-model + top-models
6. 后端读取 daily_records，按日期聚合，计算成本（单价 × token）
7. 前端 Recharts 渲染图表
```

#### 批次2 数据流

```
1. 用户在 Playground 输入提示词，选择 2 个模型
2. 前端 POST /api/playground/completions {mode:"compare", models:["a","b"], prompt:"..."}
3. 后端使用 asyncio.gather() 并发调用 litellm.acompletion() 两次
4. 收集响应、延迟、token 用量
5. 计算预估成本（基于 models.yaml 单价）
6. 返回 PlaygroundResult[]
7. 前端多栏展示，每栏显示响应文本 + 延迟/token/成本元数据
8. 同时写入 playground_history.json
```

#### 批次3 数据流

```
1. 后台启动 AlertChecker 协程（每 60s）
2. check_all() 读取 alerts.yaml 规则
3. 对每个规则计算当前 metric:
   - daily_cost: 读取今日 daily_records，sum(成本)
   - daily_requests: sum(request_count)
   - error_rate: 读取 `ErrorCounter.get_error_rate()`（内存滑动窗口）
4. 判断条件是否满足
5. 满足 → 检查冷却期 → 未冷却 → 发送通知
6. 通知通道:
   - webhook: POST JSON
   - log: 写入 alerts.log
7. 记录触发历史到 alerts_history.json
```

### 错误处理

| 场景 | 处理策略 |
|------|---------|
| `token_stats.json` v1 格式 | 自动升级到 v2：保留 `records`，新增空的 `daily_records` |
| `token_stats.json` 损坏 | 保留 `records`，`daily_records` 从当天重建，日志告警 |
| 模型未配置 `price` | 成本字段返回 `None`，前端显示 `--` |
| Playground 模型请求超时 | 返回 `error: "请求超时"`，其余模型正常展示 |
| Playground 模型返回 4xx/5xx | 返回 `error: 状态码 + 错误信息`，不计入 TokenStats |
| 告警 Webhook 发送失败 | 记录到 alerts.log，历史记录中标记 `status: "failed"` |
| `alerts.yaml` 语法错误 | 启动时跳过错误规则，日志告警，不阻断服务 |
| 告警规则 metric 不存在 | 检查时报错日志，该规则本次跳过 |

### 安全考虑

- **Webhook URL 验证**: 只允许 `https://` 协议，禁止 `http://` 和 `file://`
- **Playground 并发限制**: 最多 3 个模型同时对比，防止滥用
- **Playground 请求大小限制**: prompt 最大 10000 字符，防止超大请求
- **告警配置隔离**: `alerts.yaml` 与 `providers.yaml` 分离，避免 API Key 泄露
- **文件权限**: `token_stats.json`、`playground_history.json`、`alerts_history.json` 创建时权限设为 `0o600`

## 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| token_stats.json 在 v1→v2 升级时丢失数据 | 高 | 升级前自动备份到 `token_stats.json.v1.bak` |
| Playground 并发请求触发服务商速率限制 | 中 | 限制最多3个模型，增加 500ms 间隔 stagger |
| Webhook 泄露敏感信息到第三方 | 中 | 强制 HTTPS，payload 中不包含 API Key |
| alerts.yaml 语法错误导致服务启动失败 | 中 | 解析错误时跳过错误规则，日志告警，不阻断 |
| 前端图表大数据量渲染卡顿 | 低 | 限制最大查询 90 天，后端聚合后返回 |
| Playground 历史记录文件过大 | 低 | 限制最多 50 条，自动 FIFO 淘汰 |

### 决策记录

**决策**: Token 统计采用 JSON 文件存储，不引入 SQLite/PostgreSQL
**原因**: 项目定位为轻量级网关，保持零外部依赖；数据量小（每日几十条），JSON 足够
**替代方案**: SQLite（考虑过，但增加部署复杂度和 schema 迁移负担）

**决策**: Playground 并发请求不取消未完成的请求
**原因**: 用户需要对比所有模型的完整响应；取消会导致部分结果缺失
**替代方案**: 首个响应后取消其余（延迟更低，但体验不完整）

**决策**: 成本计算使用内置单价（models.yaml），不对接服务商账单 API
**原因**: 国内服务商（阿里云、Moonshot、智谱）大多没有公开账单 API；实现成本高、延迟大
**替代方案**: 对接服务商账单 API（P4 远期目标）

**决策**: 告警系统只支持 Webhook 和日志，不支持邮件/SMS
**原因**: Webhook 可以转发到钉钉/飞书/Slack，覆盖大部分通知场景；邮件/SMTP 增加配置复杂度
**替代方案**: 引入 SMTP 支持（可后续扩展）

**决策**: 三个批次按"数据层 → 交互层 → 监控层"顺序实现
**原因**: Playground 的成本展示和告警的阈值检测都依赖分析仪表盘的数据层；先做数据层避免重复工作
**替代方案**: 独立并行实现（效率低，数据层需要改三次）
